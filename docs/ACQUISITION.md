# Полнота получения данных

Этот пакет — первый этап общего обхода страниц. Он **не подтверждает**, что все
источники уже собираются полностью. На текущем снимке реестра 99 источников:
93 обычных сборщика и 6 отдельных pipelines. Предыдущие оценки 94/5 устарели.
Функция `app.acquisition_catalog.acquisition_catalog()` формирует список прямо
из реестра, без запросов, credentials и выдуманных зелёных статусов.

## Что меняется

- BG comps: лимит подробностей больше не отбрасывает остальные строки списка.
  При 45 найденных сборках и `detail_limit=40` возвращаются все 45, дополнительные
  запросы остаются ограничены прежним лимитом. Оба пути сбора исправлены.
  `detail_status` различает `fetched`, `empty`, `failed`, `missing_url`,
  `listing_cards`, `not_requested`; `source.details_not_requested` показывает
  оставшуюся вне бюджета часть. Это полнота найденного списка, не доказательство
  получения всех существующих страниц сайта или полноты каждой карточки.
- Общий `scrape_source_with_options(..., browser_plan=...)` принимает явный план
  ожидания/действий Scrape.do. Без плана прежний порядок провайдеров сохраняется.
  С планом выполняется одна попытка Scrape.do, без автоматического повтора или
  перехода к провайдеру, который игнорирует действия. Биллинговые наблюдатели
  продолжают получать сведения об ошибочных оплаченных ответах.
- `collect_wordpress_history()` получает продолжения WordPress REST, нормализует
  колоды и возвращает результат ParsesUnix с checkpoint и признаком завершения.
  Это отдельный внутренний режим: расписание, БД, публичная выдача последних
  20 колод каждого формата и публикационные проверки не переключаются.

## Динамические таблицы

```python
from app.browser_acquisition import BrowserAction, BrowserPlan
from app.firecrawl_backend import scrape_source_with_options

# Иллюстрация: реальные селекторы подтверждаются отдельно для каждого источника.
plan = BrowserPlan(
    wait_selector="#rows",
    actions=(BrowserAction("Click", selector="#next"),
             BrowserAction("WaitSelector", selector="#rows", timeout_ms=1000)),
)
result = await scrape_source_with_options(source, browser_plan=plan)
```

Разрешены Click, Select, ScrollY и WaitSelector; до 10 действий, до 60 секунд
суммарных явных ожиданий. Произвольный JavaScript не поддерживается. Планы —
внутренние проверенные конфигурации адаптеров, не параметры публичного API.
Каждый план требует `wait_selector` для проверки готовности итогового HTML;
план только с действиями, без этого условия, отвергается до запроса.
Click сам по себе не гарантирует отсутствие записи: настраивать его можно
только на подтверждённые элементы чтения (вкладки/пагинация), не формы действий.

Scrape.do может вернуть HTTP 200, хотя действие не выполнено: проверяем длину
`actionResults` и строгое `success=true` у каждого элемента. Дополнительно
проверяем присутствие `wait_selector` в итоговом HTML. Это структурная готовность,
не доказательство выбранного рейтинга/патча: адаптер по-прежнему обязан проверить
фильтры и содержимое. Нажатие нескольких вкладок возвращает последнюю страницу,
а не объединение: каждое представление должно собираться отдельно.
См. [действия Scrape.do](https://scrape.do/documentation/headless-browser/browser-interactions/)
и [ожидание](https://scrape.do/documentation/headless-browser/wait/).

## Многостраничная история WordPress

`app.paged_acquisition.collect_wordpress_history(client, format_name="Standard",
category_id=3)` поддерживает Standard/3 и Wild/13, размер страницы 1–100.
Он проверяет `X-WP-Total`, `X-WP-TotalPages`, размер каждой страницы и категории,
сохраняет сортировку ID по возрастанию и удаляет повторы по ID записи.
Редиректы отключены. Пропавшие/противоречивые заголовки или ошибки дают
незавершённый результат, а не усечённый «успех».
См. [контракт WordPress](https://developer.wordpress.org/rest-api/using-the-rest-api/pagination/).

Лимиты ParsesUnix по умолчанию: 5 логических запросов за запуск, 10 000
уникальных записей суммарно, 60 секунд. `resume=result.cursor` продолжает с
незавершённой страницы; `checkpoint` передаётся как async callback.
Состояние доверенное внутреннее, его хранение/сериализация — ответственность
вызывающего job. Его нельзя принимать непосредственно от публичного клиента.
Без callback сохраняется только возвращённый результат; автоматического
сохранения на диск здесь нет. Лимит запросов не равен количеству Scrape.do credits.

Чтение живой WordPress базы не является транзакционным снимком: изменение
числа публикаций останавливает сбор, но изменения содержимого при неизменном
числе публикаций этими заголовками не обнаруживаются. Для публикации истории
нужны отдельные snapshot/storage policy и авторизация её включения.

## Зависимость и проверка кандидата

Новый runner находится в candidate ParsesUnix, но отсутствует в опубликованном
wheel 0.10.2. Не подменяем релиз и не указываем несуществующий артефакт.
Без нового runner исторический режим завершается явной ошибкой **до запросов**;
остальные маршруты продолжают использовать закреплённую версию.

```sh
# Из API checkout, путь указывает на candidate ParsesUnix, не production.
PYTHONPATH=/srv/projects/tasks/parsesunix-acquisition-20260905/src make check
make security
```

Интеграционные тесты `test_paged_acquisition.py` с опубликованным старым wheel
явно пропускаются (тест отсутствующей возможности выполняется всегда).
Пропуск не является проверкой новой пагинации: перед выпуском обязательны тесты
с candidate runner, затем новый релиз core и обновление pin/checksum API.
