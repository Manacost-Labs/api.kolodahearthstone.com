# API performance baseline

`scripts/benchmark_api.py` измеряет latency и размер ответов публичных GET
endpoints. Отчёт содержит min, p50, p95, p99, max, HTTP statuses и средний
размер body для каждого сценария.

Локальный smoke benchmark:

```bash
make benchmark-smoke
```

Произвольный локальный сценарий:

```bash
.venv/bin/python scripts/benchmark_api.py \
  --base-url http://127.0.0.1:8000 \
  --path '/v1/battlegrounds/heroes?limit=50' \
  --requests 100 \
  --concurrency 10
```

Remote target требует явного `--allow-remote`. Для него жёстко ограничены
максимум 100 запросов на сценарий и concurrency 20. Полный load/soak test
production этим инструментом запрещён; для высокой нагрузки используется
отдельное staging-окружение с копией данных.

Начальный бюджет до накопления production-истории:

| Класс запроса | p95 |
| --- | ---: |
| Cached public GET | до 100 ms |
| Обычный REST GET | до 200 ms |
| GraphQL экран приложения | до 300 ms |

Числа baseline сохраняются как CI artifact или operational report, а не
коммитятся в документацию: измерение зависит от hardware, объёма базы и
состояния кэша.

## Runtime budgets и Redis

Публичные GraphQL query кэшируются на 60 секунд: маленький LRU‑слой остаётся в
процессе API, а Redis делит ответы, Persisted Queries и rate counters между
workers. При недоступности Redis API продолжает работать с локальным bounded
fallback; durable месячные квоты токенов остаются обязательными.

GraphQL до обращения к PostgreSQL проверяет depth, aliases, число токенов и
weighted cost. По умолчанию максимальная стоимость — 5 000, body запроса —
64 KiB, body ответа — 2 MiB, timeout — 8 секунд. Значения задаются переменными
`HS_GRAPHQL_*` из `.env.example` и должны изменяться только вместе с benchmark и
наблюдением p95/p99.

## Панель и `/v1/health`: где терялось время

Замер 2026-10-27. Прод — read-only: `curl` к `127.0.0.1:18081` и `cProfile`
сборки диагностики в контейнере. Панель — локально: собранный standalone
`panel-next` на фикстуре `tests/fixture-server.mjs` с задержкой 300 мс на
каждый вызов адаптера и журналом начала и конца вызовов. Прямой замер SQL
`next-data.php` на проде и снимка `/admin/parser-control` не выполнялся:
нет доступа к сессии и к чтению прод-базы.

| Экран / вызов | Шаг | Было | Причина | Стало |
| --- | --- | ---: | --- | ---: |
| `/v1/health`, `/v1/system/health` | сборка диагностики при промахе кэша (раз в 15 с) | 1,6–6,6 с | разбор ~260 МБ JSON всех datasets (3,8 с), семантическая валидация (2,8 с), повторное чтение `stale_monitor` (1,7 с) и `fetched_at` всех public datasets (1,3 с), всё в запросе | ~1–2 мс, снимок обновляется в фоне |

Тесты: `tests/test_health_snapshot.py` (TestClient, настоящий каталог
данных, подменены только часы) и `panel/tests/test_next_data_session_lock.py`
(настоящий `next-data.php` на `php -S`, файловая сессия, вместо MariaDB —
сокет, который не отвечает). Оба падали на коде до правки: устаревший
`/v1/health` пересобирался в запросе, `/demo/overview` пересобирался на
каждый вызов, `session` ждал зависший запрос каталога. Инварианты снимка —
property-based на Hypothesis (`tests/test_stale_while_revalidate.py`).

Что изменено:

- `app/stale_while_revalidate.py`: снимок в памяти процесса. До 15 с он
  отдаётся как есть. До 10 мин отдаётся сразу, а одна фоновая сборка его
  обновляет. Старше 10 мин или отсутствует — собирается в запросе, и
  параллельные вызовы ждут одну сборку. Ошибка фоновой сборки оставляет
  прежний снимок. Через него идут диагностика `/v1/health`, `fetched_at` в
  `meta` и `/demo/overview`. После старта процесса снимки собираются в
  одном фоновом потоке, поэтому первый запрос после деплоя не ждёт.
  Возраст снимка — заголовок `X-Health-Snapshot-Age` (на `/v1/health` и
  `/v1/system/health`). Admin `/ops/health` отдаёт тот же снимок без
  заголовка. Поэтому клиент, который опрашивает раз в N секунд, видит
  данные возрастом до N секунд (не больше 10 мин). В `test` окружении
  кэш выключен, как и раньше.
- `next-data.php` для чтений (GET, кроме `api_tokens`, который пишет nonce
  формы) сохраняет обновлённый `last_seen_at` и отпускает lock сессии до SQL
  (`panel_next_release_session_lock`). Lock отпускается, только если все
  токены ответа уже есть в сессии: первый запрос новой сессии создаёт их под
  lock, как раньше. Проверка входа, CSRF и мутации не изменены.

Не сделано, требует файлов вне этой правки:

- `app/page.tsx`, analytics: запрашивать `analytics_registry` и данные модуля
  параллельно (`Promise.all`; ключ модуля всё равно проверяет PHP), экономия
  одного round trip к PHP.
- `app/page.tsx`, parsers: `Promise.all([getSession(), serverData('parsers', …)])`.
- `app/layout.tsx`: Belwe и Benguiat отдаются как TTF (135 и 188 КБ);
  WOFF2-версии примерно вдвое меньше.
- `analytics.php` и `parser-control.php` тоже держат lock сессии всё время
  запроса, включая ожидание FastAPI (до 10–15 с). Им нужен тот же вызов
  `panel_next_release_session_lock()` после проверки входа (у
  `parser-control.php` — только для GET).
- `/admin/parser-control` (экран «Парсеры») читает каждый dataset при каждом
  опросе. Время не измерено; кандидат на тот же снимок.
- Сборку диагностики можно удешевить, кэшируя разбор и валидацию по
  `(inode, size, mtime_ns)` файла: сейчас она по-прежнему занимает ~4 с CPU
  раз в 15 с, пока endpoint опрашивают.
- MariaDB общая с WordPress: в slow log ~17 тыс. записей пользователя
  WordPress против 912 у панели, обычные `INSERT` занимают 3–5 с. Это
  конкуренция за диск и блокировки на уровне сервера БД, а не запросы панели
  (их таблицы на 2–15 тыс. строк, фильтры индексированы).
