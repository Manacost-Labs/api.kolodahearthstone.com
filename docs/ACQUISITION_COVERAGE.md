# Покрытие источников и адресная дозагрузка

Внутренний, явно включаемый слой поверх [обхода страниц](ACQUISITION.md).
Он не меняет публичный API, admin-панель, production БД, расписания или правила
публикации. Все источники входят в карту реестра, но первый подключённый адаптер
дозагрузки — BG comps. Это не заявление о полном сборе всех 99 источников.

## Карта покрытия

`source_view(source, snapshot_id=..., patch_id=...)` задаёт точную область сбора.
Её идентификатор включает исходный URL с query/fragment, источник, патч и
идентификатор снимка. Неизвестный патч остаётся `null`, а не угадывается.
Один snapshot_id обозначает неизменяемый снимок: новый сбор/набор данных должен
получать новый ID. Завершённая очередь старого снимка не является кэшем навсегда.

`ListingEvidence` передаётся доверенным адаптером после проверки источника.
`exhausted` означает подтверждённый конец списка, `view_confirmed` — проверенные
фильтры/вкладку. Эти флаги нельзя выставлять только на основании HTTP 200 или
количества строк. Типы, идентификаторы, соответствие области, дубли и числа
проверяются повторно при построении отчёта.

`coverage_report` разделяет:

- `unknown`: нет подтверждённого результата списка; количество и процент — null;
- `partial`: список/фильтры не подтверждены или подробности ещё не получены;
- `complete_for_view`: подтверждены список и фильтры конкретного снимка,
  все подробности получены либо их отсутствие подтверждено адаптером.

Процент не вычисляется при неизвестном знаменателе. Даже при известном числе
100% строк не доказывают правильность фильтров или получение всех подробностей.
Отчёт не подтверждает свежесть, другие рейтинги, все поля объекта или публикацию.

## Очередь подробностей

`DetailQueue(Path(...))` создаёт отдельную SQLite очередь **только по явно
переданному пути**. Не передавайте путь к основной БД: чужие таблицы отвергаются.
Существующие convergence-таблицы не используются и не изменяются.

Ключ задания — `(scope_id, entity_id)`. Повторная постановка сохраняет успех и
результат, а изменение URL/политики того же задания отвергается. Захват атомарный;
lease-token защищает от записи устаревшего исполнителя. По истечении lease
задание возвращается к повтору либо становится failed по лимиту попыток.
Состояния: pending, running, retry, succeeded, absent, failed.

Каждый claim расходует попытку. Предел по умолчанию — 3, допустимо 1–10;
batch до 10 000 записей, результат до 256 KiB строгого JSON. Ошибки сохраняются
как фиксированные коды, не исходные исключения с URL/секретами. `absent` требует
подтверждающего кода; пустой HTML сам по себе не подтверждает отсутствие данных.

`credits_spent` суммирует переданные известные/оценённые транспортом credits.
`unknown_cost_attempts` отдельно считает попытки без достоверного значения,
включая умершего исполнителя; неизвестная стоимость не считается нулевой.
Нет очистки/retention или автоматического удаления результатов: перед длительным
включением понадобится отдельная политика хранения завершённых снимков.

## BG-адаптер

```python
from pathlib import Path
from app.acquisition_coverage import source_view
from app.acquisition_detail_queue import DetailQueue
from app.bg_detail_acquisition import prepare_bg_details, drain_bg_details, bg_detail_report
from app.sources import SOURCE_BY_ID

view = source_view(SOURCE_BY_ID["hsreplay_battlegrounds_comps"],
                   snapshot_id="explicit-capture-id", patch_id=None)
queue = DetailQueue(Path("/explicit/local/path/bg-details.sqlite"))
prepare_bg_details(queue, view, listing_rows)
# Сетевой вызов: запускать только после разрешённого включения и проверки бюджета.
await drain_bg_details(queue, view, max_requests=5, max_seconds=60)
report = bg_detail_report(queue, view, listing_rows)
```

Готовыми считаются подробности с валидными core cards и непустым how_to_play.
Пустые addon/другие необязательные разделы не превращаются в выдуманные значения.
Список и tier сохраняются, результаты объединяются без изменения исходных rows.
Подробности с готовым набором полей не ставятся в очередь. Успешные результаты
переживают повторный запуск и перезапуск процесса.

Каждое задание делает один явный вызов Scrape.do; каскада провайдеров и скрытого
цикла повторов здесь нет. URL и конечный URL сверяются с ID BG-сборки, внешние
адреса/query/fragment в заданиях отвергаются. Идентификаторы карт в art-изображениях
сохраняются при преобразовании HTML в Markdown: общий конвертер их теряет.
Числовой `comp_id`, строковый `id` и номер в URL должны совпадать до постановки
в очередь; подробности не могут перезаписать идентификаторы строки списка.

Пустая/заблокированная страница идёт в retry, не в absent. Ошибка аккаунта
останавливает batch. Повтор откладывается на 180 секунд; после timeout batch
останавливается. Отмена оставляет lease для безопасного восстановления.
Лимит времени ограничивает ожидание и последующие запросы, но не может физически
остановить уже запущенный urllib-поток. Такой запрос может завершиться у провайдера
позже; стоимость учитывается как неизвестная. Это не обещание лимита credits.

## Просмотр без сети и записи

```sh
.venv/bin/python scripts/acquisition_coverage_report.py --snapshot-id inspection-1
```

Команда возвращает JSON для всех зарегистрированных источников, по умолчанию
unknown. Она не открывает БД и не делает запросов. Для одного источника доступны
`--source-id`, `--patch-id`, `--evidence /explicit/sanitized-capture.json`.
Файл содержит scope_id, entity_ids, exhausted, expected_count, view_confirmed,
detail_states. Чужая область и противоречивые данные отклоняются.

## Что остаётся отдельным этапом

Admin-панель/API endpoint для отчёта; подключение остальных семейств и pipelines;
реальные capture/replay каждого варианта страницы; retention; включение расписания.
Сбор XHR через [Scrape.do ReturnJSON](https://scrape.do/documentation/headless-browser/returnjson/)
ещё не реализован: нет подтверждённого образца структуры сетевых ответов.
Непроверенные поля ответа не угадываются. Платных/live запросов при разработке нет.
